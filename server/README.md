# Local-first account and sync service

Internal development service: Go 1.26.5, Kratos v3.0.0, PostgreSQL 18.6, sqlc v1.31.1 and pgx v5.11.0. The service stores account-scoped replicas; SQLite and the existing TypeScript Scheduler continue to run on each device. It does not run a cloud scheduler or an AI proxy.

## Run locally

```bash
cd server
cp .env.example .env
set -a
. ./.env
set +a
make db-up
make migrate
make run
```

HTTP listens on `127.0.0.1:8000`, gRPC on `127.0.0.1:9000`; Compose exposes only the development PostgreSQL port `127.0.0.1:5548`. Apply migrations separately. `make db-down` stops the dedicated database and preserves its volume. Never use the example password or signing key for a deployed service.

For iOS Simulator use `EXPO_PUBLIC_CLOUD_API_URL=http://127.0.0.1:8000` when starting Metro. Android Emulator uses `http://10.0.2.2:8000`; expose the local service to that development host only when needed. A physical device needs an explicitly reachable development origin. Production builds require HTTPS and have no default public service origin.

Open Settings → 账号、云端同步与设备提醒. The login screen explains the full upload scope. Login automatically claims an unclaimed guest profile once and starts foreground synchronization. Separate account databases and the original guest database remain on the device. The non-secret profile index uses a separate SQLite catalog; credentials remain in SecureStore. iOS Simulator authentication requires a Keychain-capable development signature. Logout stops synchronization and removes the active credential; it does not delete account facts. Existing account profiles do not automatically absorb subsequently created guest data.

Email verification and password recovery are intentionally unavailable. Registration is disabled unless `ALLOW_UNVERIFIED_REGISTRATION=true`. This is an internal test build, not a publicly deployed account system. No end-to-end encryption, cloud backup SLA or data-retention certification is claimed.

## Contracts and generated code

`api/sync/v1/cloud.proto` defines HTTP/gRPC methods; `openapi.yaml` is generated. Portable business fields are explicitly allowlisted in `contracts/entities.json`. `contracts/fixtures.json` is validated by Go and TypeScript tests. Version and cursor fields are decimal strings, not JavaScript numbers. Unknown entity fields and protocol versions are rejected.

```bash
make tools
make generate
make check
TEST_DATABASE_URL="$DATABASE_URL" make integration
```

The pinned HTTP code generator is a separate v3 module; it does not use the core module's release tag. All business queries are generated by sqlc. Goose uses pgx's stdlib adapter only for migration management. SQL migrations, generated Go and their TypeScript field manifest are checked in. Never edit generated files by hand.

## Synchronization behavior

- A local transaction is one batch. Tenant-scoped entity versions and an account-locked commit cursor fence concurrent writes. Retrying the same batch returns its original receipt; different contents with the same batch ID are rejected.
- Initial uploads are staged in chunks of 250 facts, with a deterministic authenticated staging identity so a lost response can be retried. Only commit publishes the complete graph. Download bootstrap provides a fixed snapshot. Each client persists pages in a staging table across restarts and publishes the verified graph and cursor atomically; incremental pull then returns whole committed batches. The current internal protocol caps a batch at 20,000 facts and request bodies at 16 MiB; exceeding limits fails visibly rather than partially publishing data.
- Conflicts return `conflictId` without committing facts or advancing the account head. Conflict resolution is explicit. Immutable evidence and another device's active execution are protected even when selecting the local version.
- Selecting the cloud mainline preserves the rejected local batch in a read-only conflict archive and excludes it from normal completion counts. Unresolved dependent transactions are held; unrelated work may continue. No last-write-wins policy uses device clocks.
- Full local operation receipts, OS identities/jobs/intents, calendar caches, secrets and derived features are never synchronized. A minimal operation provenance table preserves remote completion references. Plan origins are informational provenance, not remote scheduling authority.
- Each device independently enables calendar/notification projections; imported OS bindings are never copied from another device. Active execution and relax facts remain controlled by their origin device.

## Verification

The root `server:check` verifies Go formatting, vet, tests and build. `server:test:integration` requires a real disposable PostgreSQL connection and creates isolated test schemas; missing configuration fails. `server:test:sync` starts a temporary local HTTP service from TEST_DATABASE_URL (or uses an explicit CLOUD_TEST_URL) and exercises two isolated SQLite clients. It does not operate a user's database or count as physical-device E2E evidence.
